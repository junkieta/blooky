# Blooky Vision

> **「データが流れる」ことを軸に、開発体験を再設計する。**

## 1. 現代の分断された開発体験

Web 開発は成熟したように見えて、その内側では分断が進んでいます。
UI、状態管理、副作用、非同期処理、データフロー……。
それぞれが独自の概念・文法・ライフサイクルを持ち、
開発者はそれらを“翻訳”しながらプロジェクトを進めています。

この分断は、生産性だけでなく **思考の流れ** を断ち切ります。
「データがどこから来て、どこへ行くのか？」を追うたびに、
私たちは異なる文脈に飛び込まなければならないのです。

## 2. 統一された抽象 ― Stream / Prop / fx

blooky はこの分断を解くために、
**Stream（流れ）・Prop（状態）・fx（副作用）** の三つを核にした
**統一的な抽象**を提案します。

* **Stream** は出来事の流れ
* **Prop** はその時点の状態
* **fx** は外界との対話（副作用）

これらは分離したレイヤーではなく、**一つの連続したデータフロー**の中にあります。
UI・非同期処理・状態更新の境界をなくし、
「流れとしてアプリケーションを考える」ための言語です。

## 3. 開発体験の再設計

blooky が変えようと目指しているものは、単なる「書き方」ではなく、
**開発という行為そのものの体験**です。

### 概念を理解する体験

あらゆる構造は「データが流れる」という一つの原理に基づきます。
理解は直線的に深まり、断片化しません。

### 問題を分解する体験

Stream / Prop / fx が明確な責務を持つため、
どの層で問題を扱うべきかが自然に見えてきます。

### デバッグする体験

DevTools はデータフローと副作用の実行を統一的に可視化します。
「なぜ動かないのか」を追うことが、**観察すること**に変わります。

### コードを成長させる体験

小さく始めたコードは、接続を変えるだけで拡張できます。
リファクタリングは破壊ではなく、**有機的な成長**になります。

## 4. Web 標準へのリスペクト

blooky は新しい魔法を生み出すことではなく、
**Web 標準が本来持っている力を最大化する**ことを目指しています。

* jshtml は純粋な DOM API 上で動作
* fx 要素は CustomElement として実装
* イベントは標準 EventTarget 機構を利用

私たちが参照すべきドキュメントは MDN であり、仕様書です。
Web の進化と共に歩むことこそ、
長期的な持続性と学習コストの低減を両立する道だと考えます。

## 5. 統合された視座へ

blooky のゴールは単なる新しいフレームワークではありません。
開発者が「分断されたツールチェーンの翻訳者」ではなく、
**アプリケーションの流れを設計する建築家**になることです。

データが流れ、UI がそれを映し、副作用が世界と対話する。
そのすべてが一つの視座で捉えられるとき、
開発はより自然で、創造的な営みになります。


## 6. Design Principles — 設計の原則

> blooky の設計は、3つの理念に基づいている。
> **宣言性（Declarativity）**、**透明性（Transparency）**、そして **構造的一貫性（Structural Consistency）**。

---

### 1. 宣言性 — *Declare, not instruct.*

アプリケーションを「命令の集合」としてではなく、
**「状態と流れの関係」**として記述する。
開発者は「何が起きるか」ではなく、「どんな条件で何が成り立つか」を宣言する。

blooky における宣言性とは、
手続き的な指示ではなく、**意味的な構造を示す**こと。

* Stream の接続は、データの流れを宣言する
* Prop の定義は、状態の依存関係を宣言する
* fx の構成は、副作用の構造を宣言する

宣言はドキュメントであり、同時にロジックでもある。
blooky は、**読むことと動くことが一致するコード**を目指す。

---

### 2. 透明性 — *Nothing hides behind magic.*

blooky は “魔法” を避ける。
それは「仕組みを隠さない」というだけでなく、
**理解できる限界を明示する**という姿勢である。

* すべてのデータフローは追跡可能
* すべての副作用は可視化可能
* すべての状態変化は観測可能

透明性は信頼性の基盤であり、
開発者がツールの外側に出なくても、
**アプリケーション全体のふるまいを観察できる**ことが目標である。

DevTools はその思想の延長線上にある。
それは「デバッグのための特別な機能」ではなく、
**透明性という哲学を具現化するための装置**である。

---

### 3. 構造的一貫性 — *One structure, many scales.*

blooky のアーキテクチャは、
どのスケールでも同じ構造を保つ。

* 小さなコンポーネントも、大きなアプリケーションも
  **Stream → Prop → fx** の構造で語れる
* UI 層も、副作用層も、同じ抽象の中で動く
* ドメインロジックが成長しても、構造は崩れない

これにより、局所的な変更が全体の再構成を強いない。
blooky のアプリケーションは、
**自己相似的に成長できる有機体**である。

---

### 4. 拡張可能性 — *Extend by composition, not mutation.*

新しい機能を追加するとは、
既存の仕組みを「上書き」することではなく、
**既存の流れに新しいノードを加えること**。

blooky の API は、
拡張を “フック” ではなく “関数合成” で行うように設計されている。
それは柔軟さのためではなく、
**全体の一貫性を保ちながら拡張するため**の哲学である。

---

### 5. 永続する学び — *Learn once, apply everywhere.*

blooky が依拠するのは、フレームワーク特有の作法ではなく、
**Web 標準技術と関数的思考**である。
それは、学びが `blooky` に閉じないということ。

ここで得た理解は、
DOM・ECMAScript・非同期処理の原理といった
**Web の普遍的な文脈**に還元できる。
それが、blooky の「持続可能な知識体系」というビジョンに繋がる。

---

## 7. 結び ― 開発を「理解する」ための言語

blooky は、効率のための道具ではない。
それは、**理解するための言語**である。

コードを書くことは、思考を記録すること。
blooky はその思考の流れを、
データの流れとして、世界の変化として、
ひとつながりに記述するための試みだ。

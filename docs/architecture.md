# Blooky Architecture — The Design Whitepaper

**宣言的リアクティブアーキテクチャの設計原則**

---

## 1. はじめに

**blooky** は、データフロー・UI・副作用を統一的に扱う TypeScript フレームワークです。
本書は、その根底にある**設計哲学**と**アーキテクチャ原則**を明文化するものです。

目的は単に「仕様を説明すること」ではありません。
**現代のWeb開発が直面する「分断」という課題に対し、blooky がどのような思想的回答を提示するか**を示すことにあります。

この白書は、blookyの設計判断の背後にある**一貫した思考構造**を共有し、
今後の拡張・貢献・学習における**判断の基準軸**となることを目指します。

---

## 2. 設計理念

blooky の設計理念は、次の **3つの軸** に集約されます。

### 🧭 宣言性（Declarativity）

開発者は「操作」を記述するのではなく、「関係」を宣言します。
アプリケーションを命令の列としてではなく、**状態とフローの構造**として表現します。

### 🔍 透明性（Transparency）

フレームワーク内部に不可視の「魔法」を持ち込みません。
すべてのフロー、副作用、状態が**観測可能であること**を保証します。

### ⚖️ 構造的一貫性（Structural Consistency）

UI・ロジック・副作用などのレイヤをまたいでも、
**同じ抽象と構文で記述できる構造**を保ちます。

---

## 3. コアアーキテクチャ

blooky の中核は、次の3つの抽象から構成されます。

```
Stream  →  Prop  →  fx
```

| 抽象         | 役割          | 概念モデル                     |
| ---------- | ----------- | ------------------------- |
| **Stream** | 離散的なイベントの流れ | Observable / Event Stream |
| **Prop**   | 時変値（現在の状態）  | Behavior / Signal         |
| **fx**     | 世界への作用と観測   | Side Effect / Task Graph  |

これらは異なる層のための別言語ではなく、
**同一のデータフロー上で異なる位相を持つ要素**です。
すなわち、blooky は「関数型リアクティブ」と「宣言的UI」「副作用制御」を**一つの文法で結合する**フレームワークです。

---

## 4. 宣言性の実装

宣言性は「何をするか」ではなく、「どのような関係が成り立つか」を定義する設計方針として実現されています。

### 4.1. データフローとしてのアプリケーション

すべての UI・状態・副作用は、**データフローのノード**として定義されます。
これは `blooky/fp` が提供する `stream`, `hold`, `map`, `pipe` などの関数群で構築されます。

```typescript
const click$ = stream();
const $count = hold(0)(map(() => $count() + 1)(click$));
```

この構造は、リアクティブ更新・メモリ管理・型推論を
**同一の仕組みの中で統一的に扱う**ことを可能にします。

---

### 4.2. 宣言的UI (`blooky-dom`)

`jshtml` は DOM 構造を宣言的に記述する関数です。
内部的には仮想DOMを持たず、標準の `DocumentFragment` と `CustomElement` を直接利用します。

```typescript
const Counter = prime(() => ({
  div: [
    { h1: $count },
    { button: "+", $: { onclick: click$ } }
  ]
}));
```

UIもまた、**データフロー上のノード**として存在します。
レンダリングの契機は副作用ではなく、**データ変化の伝播**です。

---

### 4.3. 宣言的副作用 (`blooky-fx`)

非同期処理や外部呼び出しもまた、データフローの拡張として表現されます。
`blooky-fx` は、副作用を**階層的・視覚的なデータ構造**として表現します。

```html
<fx-sequence>
  <fx-wait ms="1000" />
  <fx-call fn="fetchUser" />
</fx-sequence>
```

この構文は、非同期処理を「見える構造」として設計図化し、
実行時には DevTools でトレース可能です。

---

## 5. 透明性の設計

透明性は、フレームワークの**観測可能性**によって担保されます。
blooky の内部はすべて `EventGraph` としてモデル化され、
その構造は DevTools から直接参照できます。

### 5.1. データフローの可視化

開発者は任意のタイミングで、アプリケーション全体のデータ構造を出力できます。

```typescript
import { dumpGraphDOT } from 'blooky/devtools';
const graph = dumpGraphDOT({ $count, click$ });
```

出力は Graphviz 形式で、ノード間の依存関係とフローを視覚化できます。

---

### 5.2. 実行時の透明性

各 `fx` 要素は実行状態を CSS のカスタムステートとして反映します。

| 状態  | CSSステート        | 意味         |
| --- | -------------- | ---------- |
| 実行中 | `:--running`   | 実行中の非同期タスク |
| 停止中 | `:--paused`    | 一時停止または待機中 |
| 完了  | `:--completed` | 成功終了       |
| 失敗  | `:--failed`    | エラー発生      |

UI上で副作用の状態が**そのまま可視化される**ことが、
「観測可能な開発体験」という設計思想を支えています。

---

## 6. 構造的一貫性の保持

blooky の構造的原則は、次の等式で表されます。

```
Component ≡ Stream + Prop + fx
```

コンポーネントとは、状態を持つデータフローの局所的な定義であり、
それを組み合わせることでアプリケーション全体が構成されます。

小規模構成から大規模構成まで、**同一構文で拡張できる自己相似性**が
blooky の核にある設計思想です。

---

## 7. 拡張の原則

blooky の API 設計は、「**合成による拡張**」を第一原則としています。

* 新しい処理を加えるときは既存 API をラップして関数合成する
* 既存挙動を置き換えるようなミューテーションは避ける
* プラグインも Graph 上の新たなノードとして定義される

この原則により、**コア抽象を乱さずに拡張可能な構造**が保たれます。

---

## 8. 設計目標としての「持続可能な学び」

blooky の学習曲線は、「**汎用的な知識の積み上げ**」によって構成されるべきです。
学ぶべきはフレームワーク固有の記法ではなく、次の基礎的知識です：

* DOM / イベント / CustomElements
* ECMAScript と非同期処理モデル
* 関数型データフロー（`map`, `filter`, `pipe`）

blooky を学ぶことは、**Web標準への投資**です。
これはツールとしての「寿命」ではなく、
**学びの持続可能性**を設計上の目標に据えています。

---

## 9. 結論

blooky のアーキテクチャは、**「分断されたWeb開発を、再び理解可能な構造へ戻す」** という試みです。

命令を排し、魔法を排し、
データの流れと副作用を**一つの視座**から記述する。

それはフレームワークである前に、
**思考を構造化するための言語**です。

---
